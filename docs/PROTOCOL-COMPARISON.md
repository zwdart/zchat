# zchat 协议与 LocalSend、IPMSG 对比

> 对比对象：
>
> - **zchat**：当前仓库的 `Protocol v1`（见 [PROTOCOL.md](PROTOCOL.md)）
> - **LocalSend**：公开的 LocalSend Protocol v2.2（默认 UDP/TCP `53317`，组播 `224.0.0.167`）
> - **IPMSG（IP Messenger）**：Shirouzu Hiroaki 的 IP Messenger 协议 Draft-9 及常见扩展（默认 UDP/TCP `2425`）
>
> 说明：LocalSend 和 IPMSG 都有多个实现和扩展，本文以公开规范/主流实现的行为为准；具体客户端可能存在差异。

---

## 1. 结论摘要

三者的定位并不完全相同：

| 项目 | 定位 | 传输模型 | 结构化程度 | 安全能力 |
| --- | --- | --- | --- | --- |
| **zchat** | 局域网聊天 + 图片/文件 | 聊天长连接 + 发送方附件服务，接收方拉取 | 高（JSON 行协议） | 无加密、无认证、令牌访问 |
| **LocalSend** | 局域网文件传输 | 接收方 HTTP(S) 服务，发送方推送 | 高（REST/JSON） | HTTPS + 证书指纹 + 可选 PIN |
| **IPMSG** | 局域网即时消息 + 文件 | UDP 消息 + 发送方 TCP 文件服务，接收方拉取 | 低（冒号分隔纯文本） | 默认无加密；可选旧式 RSA/RC2/Blowfish |

一句话概括：

- **zchat 的文件传输最像“轻量版 IPMSG 文件拉取 + 现代 JSON 聊天”**：实现小、续传自然，但没有 LocalSend 的会话确认、校验和与加密。
- **LocalSend 是标准化的文件投递协议**：HTTP/JSON、生态好、可加密、可确认，但协议较重，规范未定义断点续传。
- **IPMSG 是极简的文本协议**：兼容老设备、资源占用低、文件也支持偏移续传，但扩展性、可靠性和安全性都有限。

## 2. 文件传输：zchat vs LocalSend

### 2.1 LocalSend v2.2 的关键流程

```
发现（UDP 组播 224.0.0.167:53317，或 HTTP /register）
  -> 发送方 POST /api/localsend/v2/prepare-upload（只发元数据）
  -> 接收方决定接受/拒绝/要求 PIN，返回 sessionId + 每个文件的 token
  -> 发送方并发 POST /api/localsend/v2/upload?sessionId=...&fileId=...&token=...
  -> 接收方校验可选 sha256，落盘
  -> 失败/取消：POST /api/localsend/v2/cancel?sessionId=...
```

补充：

- 默认端口 `53317`，HTTP 或 HTTPS 由设备公布；HTTPS 使用自签名证书，证书的 SHA-256 即设备指纹。
- `prepare-upload` 支持 `?pin=123456`；接收方可用 `401`/`403`/`409` 等 HTTP 状态码表达“需要 PIN / 被拒绝 / 已有会话”。
- 文件正文是请求体裸二进制，不是 multipart；多个文件可以并行上传。
- 可选的反向下载 API：发送方提供 HTTP 页面，接收方用浏览器 `POST /prepare-download` + `GET /download` 拉取。
- 协议规范没有定义“从偏移量继续上传”的接口，因此严格按规范实现时，上传中断通常需要整文件重传；具体客户端可能自行做分块扩展。

### 2.2 文件传输能力对比

| 维度 | zchat | LocalSend v2.2 |
| --- | --- | --- |
| 发现 | UDP 组播 `239.255.77.77:42223` + 定向广播 + 受限广播 | UDP 组播 `224.0.0.167:53317`；失败时 HTTP `/register` 扫描 |
| 文件传输协议 | 自定义 TCP：一行 JSON 请求 + 裸字节流 | HTTP/HTTPS：REST + 裸二进制请求体 |
| 服务端角色 | **发送方**运行附件服务，接收方拉取 | **接收方**运行 HTTP 服务，发送方推送 |
| 谁需要入站端口 | 发送方 | 接收方 |
| 默认端口 | 42225（可被占用后随机） | 53317 |
| 断点续传 | **原生支持**：请求带 `offset`，从 `.part` 大小继续 | 规范未定义；通常整文件重传 |
| 完整性校验 | 仅校验最终字节数；无 hash | 元数据可带 SHA-256，接收方不匹配返回 `422` |
| 加密 | 无 | HTTPS/TLS，自签名证书 + 指纹 |
| 身份认证 | 无 | 证书指纹识别设备；可选 PIN |
| 用户确认 | 无“接收确认”步骤；拿到 token 即下载 | 接收方可接受/拒绝/要求 PIN |
| 多文件会话 | 每个文件一个 token/连接，无会话概念 | `sessionId` 统一管理多文件、并行上传、取消 |
| 取消 | 关闭连接即可；无显式取消消息 | `POST /cancel?sessionId=...` |
| 失败语义 | `ok:false` + 人类可读字符串 | 结构化 HTTP 状态码（400/401/403/409/422/429/500） |
| 浏览器直接下载 | 支持：`/t/<token>/<name>`，带 Range | 支持反向下载页面与下载 API |
| 协议演进 | 自定义，版本号 `v=1`，无正式规范流程 | 公开规范、版本化、多个语言实现 |
| 跨平台生态 | 仅 zchat | Android/iOS/Windows/macOS/Linux/Web/CLI 等 |
| 适合场景 | 可信局域网、聊天附件、低依赖实现 | 跨平台文件互传、需要确认/加密/标准接入 |

### 2.3 zchat 文件传输的优点

1. **拉取模型对接收方友好**
   - 接收方主动连接发送方，接收方本身不需要监听端口或被防火墙放行入站。
   - 在“发送方是桌面机、接收方是临时设备”的场景下更自然。

2. **断点续传是第一等能力**
   - 请求只有 `token` + `offset`，没有额外会话状态。
   - 接收方重启后只需读取 `.part` 大小即可继续，发送方不需要记住上传进度。
   - 对大文件、弱 Wi-Fi 环境很实用。

3. **实现极小**
   - 发送方只需监听 TCP、读一行 JSON、seek、`io.Copy`。
   - 不依赖 HTTP 框架、TLS、multipart 或会话存储。
   - 对资源受限设备、嵌入式或非主流语言实现很友好。

4. **HTTP 回退兼容性好**
   - 同一个附件同时有 TCP token 和 HTTP URL。
   - HTTP 端点是普通文件下载，可直接用浏览器/`curl`/手机访问，并支持 Range 续传。
   - 旧版本只认识 `file.url` 时仍能工作。

5. **令牌持久化**
   - TCP 令牌写入 `transfers-tcp.json`，发送方重启后旧消息仍可下载。
   - HTTP 令牌写入 `transfers.json`。
   - 对“聊天记录里的老文件”比较友好。

6. **与聊天语义结合紧密**
   - 附件元数据直接挂在消息上，进度、撤回、删除可以按消息粒度管理。
   - 不需要先建立“传输会话”再关联到聊天消息。

7. **无 TLS 负担**
   - 在可信局域网内少一层证书/信任配置，减少移动端和自签名证书兼容问题。

### 2.4 zchat 文件传输的缺点

1. **没有加密和认证**
   - 文件在局域网内明文传输。
   - 令牌是唯一凭证，泄露即可下载；不校验来源 IP。
   - 无法证明“下载到的文件确实来自声称的设备”。

2. **没有内容校验**
   - 只比较最终大小，文件损坏、磁盘错误、发送方文件被替换都可能被当成成功。
   - 没有 SHA-256/MD5，也没有 mtime/ETag 语义。

3. **没有接收确认**
   - 接收方不会弹“是否接受文件”；知道 token 就能拉取。
   - 不适合不受信任的共享网络，也缺少 LocalSend 那种 PIN/拒绝流程。

4. **没有会话与批量语义**
   - 每个文件独立 token、独立连接；多文件没有统一 session、并发控制、整体取消。
   - 失败重试策略由客户端自行决定。

5. **发送方必须在线且可达**
   - 发送方休眠、退出、防火墙拦截、端口变化都会导致下载失败。
   - 没有中继/离线存储。

6. **错误码已稳定，但覆盖面仍有限**
   - 附件响应已带稳定 `code`（`not_found`、`file_missing`、`bad_offset`、`io_error` 等），跨语言程序可直接分支。
   - 仍缺 `file_changed`、`checksum_mismatch`、`too_large`、`busy` 的实际返回；HTTP 回退目前只在 `404` 带 `X-Zchat-Error-Code`。

7. **协议私有、生态小**
   - 没有公开的 OpenAPI/IDL/参考测试集。
   - 第三方实现需要阅读 Go 代码和本文档。

8. **缺少传输层扩展**
   - 没有限速、分块校验、断点元数据、优先级、并发上限等标准字段。
   - 没有 IPv6 发现和完整的 IPv6 地址处理。

### 2.5 LocalSend 的优点

1. **标准化、生态成熟**
   - 公开 REST 规范，已有大量跨平台实现；接入成本低，调试直观。
   - HTTP 工具（curl、Postman、抓包）即可分析。

2. **安全能力完整**
   - HTTPS + 证书指纹识别设备；可选 PIN。
   - 接收方可以接受、拒绝、限制并发会话。
   - 适合不完全可信的局域网。

3. **文件完整性与错误处理更好**
   - 元数据可带 SHA-256；校验失败有明确 `422`。
   - HTTP 状态码语义清晰，便于程序化处理。

4. **多文件会话**
   - `sessionId` 统一管理多文件，支持并行上传、整体取消。
   - 更适合“一次发送一批文件”的产品体验。

5. **双向/浏览器兼容**
   - 既支持发送方推送，也支持反向下载 API 和浏览器访问。
   - 对没有安装 LocalSend 的接收方更友好。

6. **发现方式有兜底**
   - 组播失败时可以通过 HTTP `/register` 扫描局域网地址。
   - 对屏蔽组播的网络更鲁棒。

### 2.6 LocalSend 的缺点

1. **协议栈更重**
   - 需要 HTTP 服务器、TLS 证书、JSON 序列化、会话状态、PIN/接受 UI。
   - 对小型嵌入式实现不如 zchat 轻。

2. **规范没有定义断点续传**
   - 上传中断通常要整文件重传；大文件在弱网下体验不如 zchat。
   - 虽然有 Range 下载 API，但上传 API 本身不是可续传的分块协议。

3. **接收方必须是服务端**
   - 接收方要监听端口；如果接收方在受限网络/防火墙后，发送方可能连不上。
   - 与 zchat“只有发送方开端口”的模型相反。

4. **交互式中断**
   - 接收确认/PIN 提升安全，但增加了无人值守场景的摩擦。
   - 自动化集成需要处理 `401/403/409` 和用户确认状态。

5. **自签名证书的兼容性成本**
   - 移动端、浏览器、不同 TLS 库对自签名证书和指纹校验的处理不完全一致。
   - HTTP 模式虽然简单，但失去加密。

6. **只解决文件，不解决聊天**
   - 没有消息、会话、群聊、已读、输入状态等语义；聊天产品仍需另一套协议。

### 2.7 适用场景建议

| 场景 | 更合适的选择 | 原因 |
| --- | --- | --- |
| zchat 内部聊天附件 | zchat | 与消息、撤回、进度、HTTP 回退集成紧密 |
| 大文件、弱网、频繁中断 | zchat | 原生 offset 续传，成本低 |
| 跨平台、对外提供标准接口 | LocalSend | 公开 REST、生态和工具链成熟 |
| 不可信局域网、需要 PIN/加密 | LocalSend | HTTPS + 指纹 + PIN |
| 资源受限设备、最小依赖 | zchat | 一行 JSON + 裸流即可 |
| 需要一次发送多文件并统一取消 | LocalSend | sessionId 模型更完整 |
| 需要浏览器直接下载 | 两者都可 | zchat 的 `/t/...` 更简单，LocalSend 的下载 API 更标准 |

### 2.8 互操作与演进建议

如果希望 zchat 与 LocalSend 互通，建议做**网关/适配器**而不是改 zchat 主协议：

- **zchat -> LocalSend**
  - 把 zchat 的 `file` 消息转换成 LocalSend 的 `prepare-upload` 元数据。
  - 在适配器内读取 zchat 附件（TCP 或 HTTP），再作为 LocalSend 的 upload 请求体推送。
  - 把 zchat 的 token/URL 映射为适配器内部的临时文件句柄。

- **LocalSend -> zchat**
  - 适配器实现 LocalSend 的接收端 HTTP API，落盘后调用 zchat 附件服务登记文件，生成 zchat `file.token`。
  - 再向聊天会话注入一条 `kind=file` 或 `kind=image` 的消息。
  - 把 LocalSend 的 SHA-256 保存在本地扩展字段或消息文本中，zchat 原生接收方会忽略未知字段。

- **不建议直接让 zchat 说 LocalSend 协议**
  - 两者的服务端角色相反（发送方拉取 vs 接收方推送），会话/确认语义也不同。
  - 直接改造会破坏 zchat 现有的“消息携带 token + 接收方拉取”模型。

zchat 自身可优先补强的点：

1. `File` 增加可选 `sha256`，接收方完成后校验。
2. 传输错误使用稳定 `code` 字段（已实现：`not_found`、`file_missing`、`bad_offset`、`io_error` 等），保留 `error` 作文本。
3. 增加 `mtime`/`size` 的一致性校验，避免文件被替换（对应预留码 `file_changed`）。
4. 可选增加“接收确认/PIN”与会话 ID，用于不完全可信网络。
5. 可选支持多文件会话和并发上限（对应预留码 `busy`、`too_large`）。
6. 为 HTTP 回退补齐稳定错误码头（当前仅 `404` 带 `X-Zchat-Error-Code`）和 `ETag`/`Last-Modified` 语义。

## 3. 图文聊天：zchat vs IPMSG

### 3.1 IPMSG 的关键机制

IPMSG 使用 UDP/TCP 默认端口 `2425`，消息是**冒号分隔的纯文本**：

```
版本:包编号:用户名:主机名:命令字[:附加信息]
1:100:shirouzu:jupiter:32:Hello
```

主要特点：

- UDP 用于发现和消息：`BR_ENTRY`、`BR_EXIT`、`ANSENTRY`、`BR_ABSENCE`、`SENDMSG`、`RECVMSG`、`READMSG`、`DELMSG` 等。
- 命令字是 32 位整数：低 8 位是功能，高 24 位是选项位（如 `SENDCHECKOPT`、`SECRETOPT`、`FILEATTACHOPT`、`ENCRYPTOPT`、`UTF8OPT` 等）。
- 文件通过 `IPMSG_FILEATTACHOPT` 附加在 `SENDMSG` 后：
  `fileID:filename:size(hex):mtime(hex):fileattr(hex)[:ext...]`
- 接收方通过 TCP 连接发送方同一个端口，发送：
  `packetNo:fileID:offset`（十六进制）
  发送方返回裸字节；`offset` 天然支持断点续传。
- 支持目录传输（`GETDIRFILES`）、`RETPARENT` 等。
- 可选加密：RSA 公钥 + RC2/Blowfish 会话密钥；历史上还有 Shift-JIS/UTF-8 编码差异。

### 3.2 聊天能力对比

| 维度 | zchat | IPMSG |
| --- | --- | --- |
| 传输层 | TCP 长连接 + UDP 发现 | UDP 消息 + UDP 发现；文件走 TCP |
| 消息格式 | 一行一个 JSON 帧 | 冒号分隔纯文本 |
| 编码 | 强制 UTF-8 | 历史为 Shift-JIS；新实现有 `UTF8OPT` 扩展 |
| 可靠性 | TCP 有序；应用层 ACK；离线队列 | UDP 不可靠；`SENDCHECKOPT` + `RECVMSG` 可选确认；无离线队列 |
| 消息大小 | 单帧 2 MiB | 受 UDP 数据报限制（通常约 64 KiB，且更小更安全） |
| 富文本/结构 | JSON 字段可扩展 | 冒号分隔，转义能力弱 |
| 一对一 | 有明确会话 ID | 有用户/主机，没有显式会话模型 |
| 群聊 | 有：群 ID、成员列表、邀请/改名/移人/解散 | 核心协议没有真正群聊；只有广播/多播和“组名”扩展 |
| 已读回执 | `read` 时间水位 | `READMSG` 打开通知；无会话水位 |
| 送达回执 | `ack`，持久化后发送 | `RECVMSG`（需 `SENDCHECKOPT`） |
| 正在输入 | `typing` | 无 |
| 撤回 | `recall`，发送端 2 分钟内 | 无；只有 `DELMSG` 丢弃通知 |
| 头像/资料 | `Peer` 含头像、签名、状态 | 无头像；有用户名、主机名、离开状态 |
| 图片 | `kind=image` 附件消息，带 MIME/宽高，可自动下载 | 作为普通文件附件；无宽高/预览元数据 |
| 文件传输 | 发送方 TCP 拉取，offset 续传，HTTP 回退 | 发送方 TCP 拉取，offset 续传 |
| 加密 | 无 | 可选旧式 RSA/RC2/Blowfish；默认无 |
| 身份认证 | 无 | 无（加密不等于身份认证） |
| 扩展方式 | 新增 JSON 字段/帧类型；版本号 | 新增命令位/扩展字段；实现差异大 |
| 发现 | 组播 + 广播 + 手动 | UDP 广播；可指定网段/端口 |
| 跨语言实现难度 | 低（JSON），但需理解业务语义 | 低（文本），但需处理编码/转义/实现差异 |
| 生态 | 仅 zchat | 大量历史客户端，跨 Windows/macOS/Linux |

### 3.3 zchat 聊天协议的优点

1. **结构化、易扩展**
   - JSON 字段天然支持新增能力；未知字段可忽略。
   - 消息、附件、群操作、回执都有明确类型，跨语言实现不易歧义。

2. **TCP 长连接带来更好的可靠性**
   - 有序、可靠传输；不需要处理 UDP 丢包/乱序。
   - 配合应用层 ACK、离线队列，聊天体验更接近现代 IM。

3. **功能完整**
   - 群聊、输入状态、已读、撤回、头像、签名、在线状态、图片预览元数据。
   - 这些在 IPMSG 核心协议里大多没有，或需要私有扩展。

4. **UTF-8 统一**
   - 避免 IPMSG 历史上 Shift-JIS/UTF-8 混用导致的乱码。
   - JSON 转义天然处理冒号、换行、引号等特殊字符。

5. **图片与文件统一模型**
   - 图片就是带 `kind=image` 的附件，复用同一套 token/续传/回退逻辑。
   - 宽高、MIME 让接收端可以直接布局，不必先下载完整图片。

6. **单播为主，减少广播风暴**
   - 消息按连接单播；群聊由发送者逐个成员发送。
   - 相比 IPMSG 的 UDP 广播，在大群/多设备场景下更可控。

7. **离线队列**
   - 对端离线时消息落本地，重连后补发；IPMSG 核心协议不提供这一能力。

8. **文件与消息解耦**
   - 大文件不占聊天通道；聊天连接始终保持轻量。
   - 附件失败不会阻塞文本消息。

### 3.4 zchat 聊天协议的缺点

1. **私有协议，没有第三方生态**
   - 不能和现有 IPMSG 客户端直接互通。
   - 需要自己维护规范、测试向量和兼容性矩阵。

2. **仍无加密/认证**
   - 明文 TCP/UDP；任何局域网设备可以伪造 `from`、消息、ACK、撤回、群操作。
   - 群成员列表没有权限校验，任何成员都能改群或解散。

3. **实现复杂度明显高于 IPMSG**
   - 需要连接管理、握手、同时拨号冲突、帧大小限制、离线队列、群状态同步、附件服务。
   - 调试成本更高。

4. **群聊一致性较弱**
   - 没有服务器，成员列表靠广播式 `group` 帧维护；并发修改最后写入者获胜。
   - 群消息先于邀请到达会被丢弃。
   - 群消息按成员逐个发送，成员多时发送端开销 O(n)。

5. **可靠性仍是“尽力而为”**
   - ACK 丢失不重传；帧进入发送队列后连接断开可能丢失。
   - 没有消息去重；网关/重连可能造成重复。
   - 已读/输入状态不持久化。

6. **协议帧上限 2 MiB，头像也走 JSON/base64**
   - 头像较大时会占用握手帧；没有独立的头像上传/裁剪机制。
   - 文本消息实际可用长度受 2 MiB 限制。

7. **IPv4 为主**
   - 发现是 IPv4 组播/广播；手动连接的 IPv6 地址格式支持不完整。

8. **依赖发送方在线**
   - 图片/文件下载依赖发送方附件服务；聊天记录中的旧文件在发送方离线时不可用。

### 3.5 IPMSG 的优点

1. **极简、资源占用低**
   - 文本协议，UDP 发现/消息，易于在老旧设备、嵌入式环境实现。
   - 不需要维护长连接和复杂状态机。

2. **历史兼容性强**
   - 大量 Windows/macOS/Linux 客户端和变种，适合与既有 IPMSG 网络共存。
   - 在只支持广播的旧局域网里也能工作。

3. **文件传输同样支持偏移续传**
   - `GETFILEDATA` 请求里带 `offset`，和 zchat 的拉取模型相似。
   - 支持目录级传输，这是 zchat 目前没有的。

4. **无服务器、零配置**
   - 广播即可发现；不需要账号或中心服务。

5. **可选加密扩展**
   - 提供 RSA + RC2/Blowfish 的加密方案，虽然老旧，但比完全明文多一层保护。

6. **消息即文件列表**
   - 附件元数据直接跟在消息后，单包即可表达“文字 + 文件”，实现直观。

### 3.6 IPMSG 的缺点

1. **文本协议脆弱**
   - 冒号是分隔符，用户名、主机名、文件名中的冒号需要特殊处理（文件名用 `::` 转义）。
   - 没有统一 JSON/IDL，字段顺序和扩展属性容易解析错。

2. **编码混乱**
   - 历史上以 Shift-JIS 为主；`UTF8OPT` 是后加扩展。
   - 跨语言/跨平台容易出现乱码，且没有强制的协商机制。

3. **UDP 消息的可靠性有限**
   - 大消息可能被分片/丢弃；`SENDCHECKOPT` 只是可选确认，不是现代意义上的可靠消息层。
   - 没有离线队列、没有消息持久化标准。

4. **功能有限**
   - 没有真正的群聊、输入状态、已读水位、撤回、头像、图片预览元数据。
   - 图片只能作为文件附件，接收端需自行判断和预览。

5. **安全能力弱**
   - 默认明文；可选加密算法老旧，密钥管理/身份认证不完整。
   - 广播消息和发现包容易被伪造/嗅探。

6. **扩展碎片化**
   - 命令位、扩展属性、编码选项在不同客户端实现不一致。
   - 新功能很难保证所有客户端兼容。

7. **广播流量**
   - 上线、离开、广播消息都会向整个网段发包；设备多时噪音大。
   - 跨网段依赖广播可达性。

8. **没有标准化 HTTP/浏览器访问**
   - 文件只能通过专用客户端拉取，不能像 zchat 的 `/t/...` 或 LocalSend 下载页那样直接用浏览器访问。

### 3.7 图片处理的差异

| 方面 | zchat | IPMSG |
| --- | --- | --- |
| 图片表达 | `kind=image` + `file` 元数据 | `SENDMSG` 的附件文件 |
| MIME | 有 | 通常靠扩展名推断 |
| 宽高 | 有 `width`/`height`，用于布局 | 无 |
| 缩略图 | 无独立缩略图，接收后本地解码 | 无标准 |
| 自动下载 | 可配置自动下载图片 | 由客户端实现决定 |
| 传输 | 独立 TCP/HTTP 附件通道 | 独立 TCP 文件通道 |
| 上限 | 受附件服务/磁盘限制 | 受实现和 UDP 消息大小限制（元数据） |

结论：zchat 的图片体验更现代，但本质上仍是“附件 + 元数据”，并没有独立的图片协议；IPMSG 则完全把图片当文件，缺少展示所需的元数据。

### 3.8 与 IPMSG 互操作的建议

如果要做 IPMSG 网关：

- **文本映射**
  - IPMSG `SENDMSG` 的附加信息 -> zchat `chat` 的 `kind=text`。
  - IPMSG 包编号 -> zchat `message.id`（可加前缀避免冲突）。
  - IPMSG `RECVMSG` -> zchat `ack`；`READMSG` 可映射为 `read`，但没有会话水位，需要网关维护。
  - 用户名/主机名 -> zchat `senderName`/`peer.name`。

- **文件映射**
  - IPMSG 附件列表 -> zchat `file` 消息；网关需要为文件生成 zchat token，或反向从 zchat 附件服务取流后按 IPMSG `GETFILEDATA` 提供。
  - `offset` 语义可以直接映射，二者都支持偏移续传。
  - 文件名中的 `:` 需要按 IPMSG 规则转义/还原。

- **无法一一映射的能力**
  - IPMSG 没有群聊：zchat 群消息只能退化为多播/逐人发送，或由网关维护虚拟群。
  - IPMSG 没有撤回/输入状态/已读水位：这些能力在网关侧会丢失或需要私有扩展。
  - 编码：网关必须明确输入/输出使用 Shift-JIS 还是 UTF-8，并处理 `UTF8OPT`。

## 5. 对 zchat 的改进优先级建议

按“投入产出比”排序：

1. **P0：内容校验**
   - `File` 增加可选 `sha256`；接收方下载完成后校验，不匹配则删除 `.part` 并报错。
   - 这是跨语言实现最容易达成一致、收益最直接的增强。

2. **P0：稳定错误码（已完成主体）**
   - 附件响应已增加 `code` 字段（`not_found`、`file_missing`、`bad_offset`、`io_error` 等已实现，`file_changed` 等预留）。
   - 保留 `error` 作为人类可读文本，避免本地化文本影响程序逻辑。

3. **P1：传输一致性**
   - 增加 `mtime` 或内容长度之外的弱校验，检测发送方文件在续传期间被替换。
   - 可选增加 `ETag`/`Last-Modified` 到 HTTP 回退。

4. **P1：可选安全层**
   - 设备配对 + 消息签名/HMAC；附件 token 绑定来源或增加短期签名。
   - 或提供“仅可信网络/需要 PIN”两种模式，参考 LocalSend。

5. **P2：多文件会话**
   - 引入 `sessionId` 和批量元数据，支持统一取消、并发上限和整体进度。
   - 这会让 zchat 更接近 LocalSend 的产品体验，但会增加协议复杂度。

6. **P2：互操作适配器**
   - 单独实现 LocalSend 网关，而不是把两套协议揉进 zchat 核心。
   - 对 IPMSG 网关同理，优先支持文本和文件，群聊/已读做降级说明。

## 6. 文件传输速度与效率对比

本节比较“同样硬件、同样网络下，实际传一个文件有多快、多省”。结论先行：

- **1 GbE 及以下、单个大文件**：三者都能接近线速，差距通常小于 10%。真正的差异来自加密开销、实现缓冲和失败重传成本，而不是协议本身。
- **大量小文件**：LocalSend 的会话模型往返更少；zchat 和 IPMSG 每文件都要重新建连，固定开销更明显。
- **弱网/中断**：zchat 的原生 offset 续传优势最大；LocalSend 规范没有上传续传，失败要整文件重传；IPMSG 规范有偏移参数，但客户端支持参差。
- **2.5G/10G 或多路径**：三者都没有分块并行，单条 TCP 流会成为上限；只有靠“多文件并发”才能继续吃满带宽。

### 6.1 决定性因素

| 因素 | 影响 | 三者差异 |
| --- | --- | --- |
| 链路带宽/无线质量 | 上限 | 相同，取决于环境 |
| 单流 TCP 效率 | 大文件吞吐 | 都走单连接；缓冲和零拷贝决定 CPU 占用 |
| 加密 | CPU 与握手 RTT | zchat/IPMSG 无；LocalSend 默认 HTTPS |
| 完整性校验 | CPU | zchat/IPMSG 无；LocalSend 可选 SHA-256 |
| 每文件往返次数 | 小文件总耗时 | zchat≈2 RTT；LocalSend 可复用连接≈1 RTT；IPMSG≈2 RTT |
| 失败重传 | 大文件实际耗时 | zchat 续传；LocalSend 从头重传；IPMSG 看客户端 |
| 并发策略 | 多文件/多图场景 | zchat 无上限；LocalSend 会话内可控；IPMSG 基本串行 |

### 6.2 大文件：单流吞吐

三者的数据通道其实很接近：都是“一条 TCP 连接 + 裸字节流”，都没有分块并行。

| 项目 | zchat | LocalSend | IPMSG |
| --- | --- | --- | --- |
| 数据通道 | 裸 TCP（`42225`） | HTTPS（`53317`） | 裸 TCP（`2425` 或辅助端口） |
| 每文件连接数 | 1 | 1（可复用 keep-alive） | 1 |
| 加密封装 | 无 | TLS 1.3（默认） | 无（旧扩展另算） |
| 缓冲 | 256 KiB + `SetNoDelay` | 由 Dart/HTTP 栈决定，通常 64 KiB 级 | 实现差异大，常见 16–64 KiB |
| 零拷贝 | HTTP 回退非续传路径可用 `sendfile`（Linux）；TCP 路径经用户态缓冲 | 由客户端/服务端实现决定 | 多数老实现无 |
| 校验开销 | 无 | 可选 SHA-256（流式，通常不是瓶颈） | 无 |

要点：

- **zchat 的 TCP 路径**：`io.CopyBuffer` + 256 KiB 缓冲，每 100 ms 上报一次进度，CPU 主要是两次内存拷贝，1 GbE 下轻松跑满。由于 `progressWriter` 包装了连接，**用不上 `sendfile`**；HTTP 回退在不带 `Range` 时直接 `http.ServeContent`，Linux 上反而可能更省 CPU。
- **LocalSend 的 TLS**：桌面 CPU 有 AES-NI 时，TLS 1.3 吞吐通常在 GB/s 级，1 GbE 下几乎无感；树莓派/低端 ARM 或无 AES 指令的设备可能降到几十 MB/s，此时会先于网络成为瓶颈。TLS 握手多 1 RTT，但可由 keep-alive 摊薄。
- **IPMSG 的瓶颈多在实现**：协议本身没有额外开销，但不少客户端缓冲小、同步写、单线程阻塞，CPU 和磁盘慢时更容易掉速；对大文件（>4 GiB）还有 32 位大小字段等历史限制。

典型量级（1 GbE 有线、SSD、无其他流量，仅作数量级参考）：

| 场景 | zchat | LocalSend | IPMSG |
| --- | --- | --- | --- |
| 1 GiB 单文件 | 105–112 MB/s | 100–112 MB/s | 60–110 MB/s |
| 4 GiB 单文件，Wi-Fi 6 | 50–90 MB/s | 50–90 MB/s | 40–80 MB/s |
| 传输中断 30% 后继续 | 只补剩余 70% | 整文件重传 | 视客户端，多数整文件重传 |

### 6.3 小文件：往返次数比带宽更重要

单个文件的总耗时近似为：

```
T ≈ N × (握手 RTT + 请求/响应 RTT + size / 带宽) + 会话固定开销
```

- **zchat**：每个文件新建 TCP（1 RTT），再发一行 JSON 请求、收一行 JSON 响应（约 1 RTT），之后才是数据。**约 2 RTT/文件**，且没有连接复用或流水线。
- **LocalSend**：一次 `prepare-upload` 协商整批文件，之后每个文件一个 `upload` 请求；HTTP/1.1 keep-alive 复用连接时**约 1 RTT/文件**。规范明确 upload 可以并行。
- **IPMSG**：每个文件重新连发送方并发送 `GETFILEDATA`（约 2 RTT/文件），无会话复用。

举例：1000 个 64 KiB 文件，总数据仅 64 MiB（100 MB/s 下约 0.7 s），但 5 ms 的 Wi-Fi RTT 下，zchat/IPMSG 的往返开销约 10 s，LocalSend 约 5 s——**小文件场景下协议往返就是主要成本**。

此外，zchat 每个文件都要做一次令牌查找和 `os.Stat`，开销很小但仍是每文件固定成本；LocalSend 的 HTTP 头比 zchat 的 JSON 行更大（几百字节），在极小文件时反而更重。

### 6.4 中断与重传成本

| 项目 | 续传粒度 | 断线后的代价 |
| --- | --- | --- |
| zchat | 字节 offset，TCP 与 HTTP 回退都支持 | 只重传缺失部分，最适合不稳定 Wi-Fi |
| LocalSend | 规范未定义上传 Range | 该文件从头重传；4 GiB 传到 80% 断线，代价仍是 4 GiB |
| IPMSG | `GETFILEDATA` 带 offset，协议层可续传 | 取决于客户端；不少实现直接整文件重来 |

在 2.4/5 GHz 干扰、休眠唤醒、切换 AP 的场景里，这一项对“实际完成时间”的影响往往大于协议吞吐差异。

### 6.5 并发与多文件

- **zchat**：接收端每个文件一个 goroutine/连接，**没有全局并发上限**。好处是实现简单、多个文件天然并行；风险是大文件、图片预览、HTTP 回退同时抢带宽和磁盘。`queueActiveImages` 会把当前会话所有缺图一次性排队下载，聊天记录里图片多时尤其明显。
- **LocalSend**：以会话为单位管理，规范允许多个 `upload` 并行，官方客户端会限制并发并结合会话锁（`409 Blocked by another session`）避免互相拖垮。
- **IPMSG**：典型实现串行、阻塞，传大文件时聊天和其他操作体验明显变差。

### 6.6 效率维度对照

| 维度 | zchat | LocalSend | IPMSG |
| --- | --- | --- | --- |
| 单流大文件吞吐 | 接近线速 | 接近线速（有 AES-NI 时） | 接近线速，取决于实现 |
| 加密开销 | 无 | 有（TLS） | 无 |
| 校验开销 | 无 | 可选 SHA-256（流式） | 无 |
| 每文件往返 | ≈2 RTT | ≈1 RTT（keep-alive） | ≈2 RTT |
| 连接复用 | 无 | HTTP keep-alive | 无 |
| 断点续传 | 原生，TCP/HTTP 均支持 | 无 | 规范有，实现不一 |
| 多文件并发 | 无限制（需自行限流） | 规范允许，客户端控制 | 串行 |
| 零拷贝 | HTTP 非续传路径可 | 取决于实现 | 通常无 |
| 弱网完成时间 | 好 | 一般 | 一般偏差 |

### 6.7 对 zchat 的提速建议

按收益从高到低：

1. **复用附件连接 / 减少 RTT（对小文件收益最大）**
   - 简单做法：允许一次请求多个 token（`{"tokens":[...],"offset":0}`），服务端按顺序流式发送，每段前加长度前缀；或对同一发送方保持长连接、管道化请求。
   - 需要新增帧或字段，建议通过 `caps` 声明后启用，旧端不受影响。
2. **有限并发 + 限流**
   - 多文件传输限 2–4 条连接，图片自动下载单独限 2–3 条；避免 `queueActiveImages` 一次拉起几十个连接。
   - 服务端同样限制同时传输数，超出返回 `busy`（见 PROTOCOL.md 11.2）。
3. **大文件走零拷贝**
   - Linux 上直接 `io.Copy(conn, f)`（目标是 `*net.TCPConn`）可触发 `sendfile`；只在需要进度时用计数 Reader，而不是包装 Writer。
   - HTTP 回退已经具备该能力，可作为大文件的首选回退路径。
4. **缓冲与 TCP 参数**
   - 256 KiB 对 1 GbE 足够；10 GbE 可调到 512 KiB–1 MiB，再大收益有限。
   - 已设置 `SetNoDelay(true)`，保持即可；不要为了“攒包”关掉它。
5. **发前预检 + 尽早回退**
   - 发送前用 `caps/limits` 检查大小、剩余磁盘、对端是否可达；TCP 建连失败立即走 HTTP，不要等超时。
6. **可选分块并行（P2）**
   - 对 2.5G/10G 或高 RTT 链路，用 Range 把单文件切成 2–4 段并行拉取，能显著提升单文件吞吐；但会增加服务端压力和实现复杂度，建议作为 `caps` 能力，默认关闭。
7. **降低固定开销**
   - 图片预览用缩略图并按需加载原图；头像限制尺寸；避免把大图塞进聊天帧与文件传输争抢带宽。

### 6.8 测量建议

要得到可信结论，至少区分以下变量：

- 文件大小：64 KiB / 1 MiB / 100 MiB / 4 GiB，分别代表“往返主导”和“带宽主导”。
- 网络：有线 1 GbE、Wi-Fi 5/6、跨 AP、有人为丢包（`tc netem` / 弱网工具）。
- 指标：完成时间、平均吞吐、CPU 占用、失败重传字节数，而不只是“峰值速度”。
- 对照：同一台机器分别用 zchat、LocalSend、IPMSG 客户端互传，避免硬件差异干扰。

---

## 7. 总结

- **zchat 的优势在“简单 + 聊天一体化 + 原生续传”**：它用很小的协议代价，把文本、图片、文件、群聊、回执、离线队列串了起来；文件拉取模型和 offset 续传非常适合局域网聊天附件。
- **zchat 的短板在“安全、标准化、生态”**：没有加密/认证、没有 hash、错误码覆盖仍不完整，第三方实现只能依赖本文档和源码。
- **LocalSend 更像一个标准文件投递协议**：HTTP/JSON、会话、PIN、HTTPS、SHA-256、错误码都更完整，但更重，且规范不强调上传续传。
- **IPMSG 是极简主义的代表**：文本协议、UDP、低资源、老设备兼容，文件续传也有；但编码、可靠性、功能和安全都停留在早期局域网时代。
- **速度上三者的差距主要不在“协议带宽”，而在细节**：大文件都能接近线速，差异来自加密（LocalSend）、实现缓冲（IPMSG 参差）和断线重传（zchat 最优）；小文件则被每文件往返次数主导，LocalSend 的会话模型更占优。

若目标是“方便跨语言对接和兼容”，zchat 最值得补的是 **hash + 错误码 + 可选安全层**；若目标是“和现有生态互通”，则应通过 **LocalSend/IPMSG 网关** 实现，而不是改动 zchat 的核心拉取模型。
